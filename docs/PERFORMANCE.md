# Performance

Speed is a core product goal. This document defines **budgets** (targets that must be met), **how they are measured**, and a log of measured results. Agents must not weaken a budget without the owner's approval (AGENTS.md §4.9).

## 1. Reference machines

| Name | Hardware | Used for |
| --- | --- | --- |
| `owner-notebook` | Owner's Windows 11 work notebook (record CPU, RAM, SSD in the results log when first measured) | Final acceptance of budgets |
| `ci-linux` | GitHub-hosted `ubuntu-24.04`, 2–4 vCPU | Regression detection only (noisy, compare relative numbers) |
| `ci-windows` | GitHub-hosted `windows-2025`, 2–4 vCPU | Regression detection only |

Budgets below are for `owner-notebook` with a **warm OS file cache** unless stated otherwise. Cold-cache numbers are disk-bound and recorded for information.

## 3. Budgets

| ID | Scenario | Budget |
| --- | --- | --- |
| P-OPEN-1 | Time from opening `small` until the first screen of lines is painted | ≤ 100 ms |
| P-IDX-1 | Full index of `small` | ≤ 150 ms |
| P-IDX-2 | Full index throughput on `large` / `short` | ≥ 2 GB/s warm cache (or ≥ 90% of a plain `read()` loop over the same file on the same machine, whichever is lower) |
| P-IDX-3 | Index memory | ≤ 2 bytes per line on `large`, ≤ 3 bytes per line on `short` |
| P-SRCH-1 | Literal filter (`"ERROR"`) on `small` | ≤ 100 ms to final result |
| P-SRCH-2 | Regex filter (`/(ERROR\|WARN).*timeout/`) on `large` | ≤ 1.0 s with all cores |
| P-SRCH-3 | Boolean filter (`/ERROR/ AND NOT "heartbeat"`) on `large` | ≤ 1.2 s with all cores |
| P-SRCH-4 | Search scales with cores: 4 threads vs. 1 thread on `large` | ≥ 3× faster |
| P-SRCH-5 | Match list memory | ≤ 2 bytes per match on average for typical match densities |
| P-UI-1 | Scrolling / paging in any test file (incl. `long`, with 20 highlight rules active) | every frame ≤ 16 ms (no dropped frames at 60 Hz) |
| P-UI-2 | UI thread blocked by any single event while indexing or searching | ≤ 50 ms |
| P-TAIL-1 | Latency from a write by another process to the line being painted | ≤ 100 ms with notifications, ≤ interval + 100 ms with polling |
| P-TAIL-2 | File growing at 50 MB/s for 60 s with a filter active | UI stays responsive (P-UI-2), memory stays bounded (index + match list only) |
| P-MEM-1 | Process memory with `large` open, filter active, idle | ≤ 150 MB + index |
| P-START-1 | Application start to empty main window | ≤ 500 ms |

## 4. How to measure

- **Benchmarks** (`bench/`, Google Benchmark, release build): `BM_Index_*`, `BM_Search_*`, `BM_LineIndex_*`, `BM_Decode_*`. They generate the data with `loggen` into a cache directory (`LV_BENCH_DATA`, default `build/bench-data/`) on first run.
- **UI timing:** debug overlay (`Ctrl+Shift+F12` in development builds) shows paint time per frame and max UI stall. A Qt Test (`tests/ui/perf_*`) asserts P-UI-1 on `ci-linux` with relaxed factors (2×) to catch gross regressions.
- **Memory:** benchmarks report `bytes_per_line` counters from the index itself; process memory via Task Manager / `/proc/self/status` noted manually.
- **CI regression check:** the CI benchmark smoke job runs a reduced set on `small`/`short` and compares with the baseline file `bench/baseline-ci-linux.json`. A slowdown of more than 25% fails the job (CI noise is high; the threshold is intentionally loose). Baselines are updated only in PRs that explain why.
- **Comparison:** before 1.0, the owner measures klogg on `owner-notebook` with the same files and records the numbers here. The goal is "not slower than klogg" on P-IDX and P-SRCH scenarios.
